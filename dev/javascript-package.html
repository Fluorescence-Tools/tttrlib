tttrlib for JavaScript (Node.js)#

A native Node.js addon built on Node-API, generated by SWIG from the same interface files as the Python, R and Java bindings. It wraps the full Python surface — core, I/O, burst search, correlation, CLSM imaging, HMM decoding, PDA, the decay fits and the photon simulator — and returns the same numbers, which is verified against the same canonical values the other three suites assert.

Note

Node ≥ 12.17. Node-API has a stable ABI, so one binary per platform serves every later Node release without a rebuild — the reason this binding targets -napi rather than SWIG’s V8 backend.

Installation#

From npm#

npm install tttrlib

Prebuilt binaries are published for linux-x64, linux-arm64 (glibc), darwin-x64, darwin-arm64 and win32-x64, resolved by node-gyp-build from prebuilds/<platform>-<arch>/. There is no compile step, no node-gyp and no per-Node matrix: Node-API’s ABI is stable across Node majors, so one binary per platform serves every Node ≥ 12.17.

The tarball ships binaries only — no C++ sources and no binding.gyp — so npm install never silently falls back to compiling. On a platform without a prebuild, require('tttrlib') fails with the target triple it could not find, and the fix is a source build.

From source#

Needs SWIG ≥ 4.2 (its Node-API backend) and the Node-API headers, which come from npm rather than from the system:

npm install --prefix ext/js/pkg
cmake -S . -B build -DBUILD_JAVASCRIPT_INTERFACE=ON
cmake --build build -j

The addon lands in build/js-pkg/tttrlib.node. ext/js/pkg/index.js finds it there without installing anything, so the tests and the example application run straight out of the build tree.

Warning

The loader takes the most recently modified build*/js-pkg/ at the repository root. A second build tree therefore captures every test run silently — an ASAN tree turned every suite red with no hint that the addon under test was not the intended one, and a -DTTTRLIB_JS_COPY_ARRAYS tree is worse, because it passes. Delete extra build trees, or set TTTRLIB_ADDON explicitly on every run.

Building a distributable binary#

A binary that has to run on a machine other than the one that built it is a different artefact, and building it by hand is the reliable way to ship something that only works locally:

node ext/js/pkg/scripts/prebuild.mjs

This configures with -DTTTRLIB_MODULE_TYPE=STATIC (one .node instead of ~35 sibling module libraries), installs rather than copies — only cmake --install rewrites the build-tree RPATHs to @loader_path / $ORIGIN — collects the remaining third-party libraries beside the addon, and then verifies that nothing it produced depends on anything outside its own directory or the operating system. It writes ext/js/pkg/prebuilds/<platform>-<arch>/node.napi[.<libc>].node, which is the layout node-gyp-build reads.

scripts/pack.mjs merges per-platform prebuilds into a publishable package, taking the version from pyproject.toml. It refuses to assemble a package missing any of the five platforms: a partial one is indistinguishable from a complete one until somebody on the missing platform installs it.

Quick start#

const tttrlib = require('tttrlib');

const t = new tttrlib.TTTR('measurement.ptu');
console.log(t.size(), 'photons');
console.log(t.macroTimes);            // BigUint64Array
console.log(t.microTimes);            // Uint16Array
console.log(t.acquisitionTime, 's');

const [decay, timeAxis] = t.getMicrotimeHistogram(1);

Five conventions#

These are the whole of what a Python user has to relearn.

64-bit values are BigInt#

Macro times exceed 253, where a JavaScript number stops being exact. They cross as BigUint64Array (they are unsigned long long in C++), and burst boundaries as BigInt64Array. Summing needs 0n as the seed:

const total = t.macroTimes.reduce((a, b) => a + b, 0n);

A Float64Array of macro times would silently round, so the input typemaps reject one rather than convert it.

Arrays are flat and row-major, with a shape#

const img = new tttrlib.CLSMImage(t, new tttrlib.CLSMSettings(), null, true,
                                  Int32Array.of(0)).getIntensity();
img.shape                              // [frames, lines, pixels]
img[(f * lines + l) * pixels + p]

The same form is accepted back as input, as are nested arrays and {data, shape} objects.

Containers become native JavaScript values#

Where Python’s binding gives a list or a dict, this one gives a TypedArray or a plain object rather than the opaque proxy SWIG’s Node-API backend produces by default:

correlator.getCorrNormalized()          // Float64Array, not a VectorDouble
extractor.getBurstChannelPhotons()      // {"0": Float64Array, "8": ...}

Map keys are strings, because JavaScript object keys are — the same shape either binding’s JSON produces.

Two names for every method, and properties for accessors#

Every method exists under its C++ name (get_macro_times) and a camelCase alias (getMacroTimes); a get_x/set_x pair also appears as a property x. Code ported from Python keeps working, and so does code written against the C++ reference.

Members declared with %attribute are properties, not getters — exactly as in Python:

t.header.micro_time_resolution         // not getMicroTimeResolution()
img.nFrames                            // not getNFrames()
correlator.nBins = 8;                  // not setNBins(8)

Everything blocks#

Every call is synchronous. Reading a 200 MB file takes seconds and blocks the event loop for all of it, so in a server put tttrlib in a worker_thread — examples/js/ptu-webapp/ shows the shape of that.

The registry: never hard-code an algorithm list#

registry() returns a machine-readable description of what this build can do: which burst searches exist, which containers it reads, and a JSON Schema of every parameter with its default, unit and range. A user interface built from it gains new tttrlib features on upgrade with no code change.

for (const name of tttrlib.burstSearchAlgorithms()) {
  const bursts = t.burstSearchByName(name);       // defaults from the schema
}

const schema = tttrlib.registry('burst_search').sliding_window.params_schema;
const containers = tttrlib.registry('file_container');

burstSearchByName dispatches through the registry’s method field, so it also reaches compositions implemented in the binding rather than in C++ — the coincident multi-detector search among them.

Zero copy, and when it isn’t#

Array results are normally views over C++-owned memory rather than copies. Two consequences:

  • A view returned by an accessor is valid only while the object it came from is alive. Reading it afterwards is a use-after-free, not an exception. Call .slice() if it must outlive its owner. (numpy.i’s ARGOUTVIEW carries the same hazard in Python.)

  • Some Node-API hosts refuse external ArrayBuffers — Electron, and builds with the V8 sandbox. The binding detects that at run time and copies instead; tttrlib.arraysAreZeroCopy() reports which mode is live, and building with -DTTTRLIB_JS_COPY_ARRAYS forces copying everywhere.

Example application#

examples/js/ptu-webapp/ is a small web viewer: open a PTU (or HT3, SPC, Photon-HDF5, …) and see its header, time trace and micro-time decay in a browser, with no Python anywhere.

node examples/js/ptu-webapp/server.mjs      # then open http://127.0.0.1:8030

It is deliberately small — one file of server, one page of front end, no framework and no build step — and it demonstrates the two decisions anything built on this binding will face: every tttrlib call runs on a worker thread, and photon arrays never leave it (binning and histogramming happen in C++, so a few thousand points cross the wire instead of a few hundred million).

It binds to localhost and reads only from one configured data root, with containment checked server-side. It is not written for network exposure.

Known limitations#

Limitation

Detail

No directors

SWIG’s Node-API backend generates none, so PdaCallback cannot be subclassed from JavaScript — the same limitation the R binding has. PDA’s built-in models are unaffected.

No Promises

Everything is synchronous; see Everything blocks above.

Not the browser

This is a native addon for Node. A WASM build is a separate question, and not a small one.

shared_ptr lifetime

An object constructed in JavaScript and handed to C++ code that stores a std::shared_ptr is passed with a null deleter: C++ holding it does not extend its life. Keep the JavaScript variable alive as long as anything C++-side refers to it. (R and Java live under the same contract — neither has shared_ptr support at all.)

std::set

SetInt32 is not instantiated for JavaScript, as it is not for R. Nothing in the wrapped API returns or takes a std::set, so this costs nothing today; it would have to be added if one ever did.

What is still open#

Kept here rather than in a tracker so it stays next to the thing it describes. Ordered by what would bite first.

Open item

Where it stands

Test coverage is not at parity

The Python suite has ~1500 test functions across 141 files; this one has ~60. It covers the same subsystems and asserts the same canonical cross-language values, which is what catches a broken binding — but it is not the file-for-file parity the phrase suggests. Closing it properly means either porting the Python suite or generating both from one shared case list.

Only macOS arm64 has been built

Linux and Windows are untried, in both the ordinary and the prebuild builds. build_test_js_lnx, prebuild_js, pack_js, publish_npm and asan_js_lnx are all written and none has run, so treat their first run as part of the work rather than as a regression check.

Nothing has been published

The pipeline exists and a packed tarball installs and works on darwin-arm64, but publish_npm needs an NPM_TOKEN repository secret that does not exist, and the name has not been claimed on the registry.

No sanitiser run

asan_js_lnx is written — Linux, LD_PRELOAD of libasan.so, detect_leaks=0, and an explicit TTTRLIB_ADDON so it cannot silently test an uninstrumented addon — and has not run. test/js/lifetime.test.mjs covers the shared_ptr and GC side in ordinary builds. macOS arm64 cannot host this: preloading the ASAN runtime into Node hangs before any JavaScript executes, with no addon loaded at all.

Testing status#

node --test test/js/

test/js/cross_language_reference.test.mjs asserts the same canonical values as test/python/tttr/test_cross_language_reference.py, test/r/test_tttr.R and the Java suite: photon counts, macro-time sums, routing channels, correlator curves, burst results, micro-time histograms and header fields, all from bh/bh_spc132.spc. A failure there means the JavaScript binding is wrong, never that the number needs updating.

tools/check_swig_multilang.sh additionally generates all four wrappers from the shared interface fragments on every change, so a Python-only construct leaking into the language-neutral core is caught without a native build.
