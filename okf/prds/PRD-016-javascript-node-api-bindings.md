## Summary

Add a fourth binding — JavaScript/TypeScript for Node.js — generated by SWIG's
Node-API (`-napi`) backend from the *same* shared interface fragments that
already produce Python, R and Java. The new code is one array-marshalling
library (`ext/js/jsarrays.i`), one top module, one CMake branch, and an npm
package.

## Problem / motivation

tttrlib's analysis core is reachable from Python, R and Java. It is not reachable
from the runtime that every browser-based tool, every Electron app and every
lab web service is written in. PRD-017 wants a burst-analysis web UI; today that
means shelling out to Python or reimplementing burst search in JavaScript, and
the second is how numbers start disagreeing between tools.

The binding architecture already anticipates this. `ext/python/misc_types.i`
picks an array library per language:

```
SWIGPYTHON → numpy.i        SWIGR → ext/r/rarrays.i        SWIGJAVA → ext/java/jarrays.i
```

All three define the **same typemap names** (`IN_ARRAY1/2/3`, `INPLACE_ARRAY*`,
`ARGOUTVIEW[M]_ARRAY*`), which is what lets ~150 `%apply` lines be shared
verbatim. A fourth language is a fourth entry in that dispatch plus the library
behind it. The interface fragments themselves should not need to change.

## Goals

1. `require('tttrlib')` in Node.js gives `TTTR`, `TTTRHeader`, `Correlator`,
   `CLSMImage`, burst search/filter, `registry()` — with the same method names
   and the same numbers as Python.
2. Photon arrays cross the boundary as **TypedArrays**, without a per-photon
   JavaScript loop anywhere.
3. Generated from the existing shared `.i` fragments; Python's generated wrapper
   stays byte-identical (the same invariant `tools/check_swig_multilang.sh`
   enforces today for R and Java).
4. Built by the existing CMake, behind `BUILD_JAVASCRIPT_INTERFACE`, linking the
   same module targets as the other bindings.
5. Publishable to npm with prebuilt binaries — one per platform, not per Node
   version, which is the whole point of Node-API.
6. Passes the PRD-015 conformance case list.

## Non-goals

- Browser/WASM. Out of scope here; see *Fork decision* for why the door is left
  open and PRD-017 for why the first consumer does not need it.
- Directors / C++-calling-JavaScript. SWIG's Node-API generator does not support
  directors or JavaScript callbacks, so `PdaCallback` subclassing is unavailable
  exactly as it is in R.
- Wrapping every module. First release covers core + io + burst + correlator +
  histogram + registry; `sim`, `hmm`, `nn`, `pda`, `superres`, `localization`
  follow once the marshalling is proven.
- Async/Promise wrappers. Everything is synchronous in v1; see *Risks*.

## Prior art / what was verified

`swig -c++ -javascript -napi` was run locally (**SWIG 4.2.1**, the version this
repo already requires) against a toy class with `std::vector<double>` and
`std::string` members: it generates a 93 KB `node-addon-api` wrapper including
the `%template(VectorDouble)` STL proxy. The `-node` (V8/NAN) backend also
generates, and is the one to avoid — it delegates to the V8 generator, has no
stable ABI, and needs a rebuild per Node major.

Support timeline, from the SWIG documentation: the Node-API generator landed in
**SWIG 4.2.0**; it requires Node-API v6 (**Node ≥ 12.17**); it gives automatic
C++→JS exception conversion, `long long` support (the only backend that has it)
and working default arguments; it does not give directors or callbacks.

## Fork decision — upstream SWIG, not SWIG JSE

There are two SWIGs that emit Node-API:

| | upstream SWIG 4.2+ (`-javascript -napi`) | SWIG JavaScript Evolution 5.x (fork) |
|---|---|---|
| relationship | the SWIG this repo already builds Python/R/Java with | a JS-only fork; its `worker_threads` support was merged upstream in 4.2.0, async is "being considered" |
| async / Promise | no | yes, `…Async()` with libuv |
| TypeScript `.d.ts` | no | yes, via `%typemap(ts)` |
| WASM / browser | no | yes, via emscripten + emnapi, same wrapper as native |
| distribution | apt/conda/brew, already in CI | conan/xpack/GitHub Action |
| status | released | "late technology preview / early public release" |

**Take upstream.** One SWIG for four languages is the constraint that matters: CI
already fights SWIG-version-dependent `int64_t` typedef resolution across three
backends (see the `-DSWIGWORDSIZE64` three-way constraint), and a second SWIG
binary in the matrix multiplies that. Hand-write the ~200-line `index.d.ts`
rather than take a fork for it.

Revisit **only** if a browser build becomes a requirement: the fork's
emscripten/emnapi path is the credible way to get `tttrlib` into a page, and it
consumes the same `.i` files, so this decision is reversible at the cost of a
build matrix, not a rewrite.

## Proposed approach

### `ext/js/jsarrays.i` — the actual work

Implement the numpy typemap names over Node-API values. The mapping:

| typemap | JS type in | JS type out | mechanism |
|---|---|---|---|
| `IN_ARRAY1(T*, int)` | TypedArray of matching type, or Array | — | `Napi::TypedArray` → `.Data()`; plain `Array` is copied, and a mismatched TypedArray type is a `TypeError`, not a silent cast |
| `IN_ARRAY2/3` | TypedArray + explicit dims, or nested Array | — | row-major, contiguous only |
| `INPLACE_ARRAY*` | TypedArray | mutated in place | `.Data()` written directly; must reject non-contiguous and honour `ByteOffset()` on sliced views |
| `ARGOUTVIEW_ARRAY*` | — | TypedArray | `napi_create_external_arraybuffer` over C++-owned memory, no copy |
| `ARGOUTVIEWM_ARRAY*` | — | TypedArray | same + finalizer that frees, so the C++ allocation follows JS GC |

The `ByteOffset()` detail is not optional: `arr.subarray(k)` shares the buffer,
and a wrapper that ignores the offset reads the wrong photons or overruns.

**Integer width.** JavaScript numbers are IEEE doubles — exact only below 2^53.
Macro times are 64-bit. Rule for v1:

- `int64`/`uint64` **arrays** → `BigInt64Array` / `BigUint64Array`. Exact,
  awkward to do arithmetic with, and correct.
- `int64` **scalars** → `BigInt` (SWIG's `-napi` backend supports `long long`).
- Reductions users actually want (sums, min/max over macro times) are computed in
  C++ and returned as `BigInt`, so nobody is tempted to `reduce()` a
  `Float64Array` and lose the low bits.

This is the JS form of the rule R already lives under, and PRD-015's runner
enforces it.

### Module structure

```
ext/js/tttrlib.i      top module, mirrors ext/{r,java}/tttrlib.i
ext/js/jsarrays.i     the array library above
ext/js/pkg/           npm package: package.json, index.js, index.d.ts, binding.gyp
```

`ext/python/misc_types.i` gains a `#ifdef SWIGJAVASCRIPT` branch selecting
`jsarrays.i`. Shared fragments that use Python-only helpers get the same no-op
treatment R and Java already have (`TTTRLIB_NOGIL`, the `PyErr_Format` shim).
Expect a first pass of `#ifndef SWIGJAVASCRIPT` guards around STL that the JS
library lacks, discovered by generating, not by reading.

### Build

A `BUILD_JAVASCRIPT_INTERFACE` branch in `ext/CMakeLists.txt`, structured like
the Java one, producing a `MODULE` library with suffix `.node`:

- include dirs from `node -p "require('node-api-headers').include_dir"` and
  `node -p "require('node-addon-api').include"`;
- `NAPI_VERSION` pinned (8 — Node 12.22/14.17+), `NAPI_CPP_EXCEPTIONS` on, since
  the exception mapping depends on it;
- `USE_SWIG_DEPENDENCIES TRUE` and `SWIG_MODULE_<target>_EXTRA_DEPS`, the
  mechanisms that actually work (the `SWIG_MODULE_DEPENDS` property does not —
  that bug cost a silent-stale-wrapper release once already);
- links the same `modules/*` targets as the other bindings, so the module rework
  in progress covers it for free.

CMake rather than `node-gyp` keeps one build system. `binding.gyp` ships in the
npm package as the fallback path for `npm install` from source.

### Packaging

npm package `tttrlib`, prebuilt binaries via `prebuildify` for
linux-x64/arm64, darwin-x64/arm64, win32-x64, loaded by `node-gyp-build`. Node-API's
ABI stability means one binary per platform covers every supported Node — the
single strongest argument for `-napi` over `-node`.

> **What was built instead of `prebuildify`.** `prebuildify` drives `node-gyp`,
> and this project's addon is a CMake target linking 35 module libraries — there
> is no `binding.gyp` to drive. Only the *output layout* matters to
> `node-gyp-build`, so `scripts/prebuild.mjs` produces that layout from
> `cmake --install` directly. See *What was built*, item 4.

### Verification

- `tools/check_swig_multilang.sh` grows a fourth generation pass, and asserts
  the Python wrapper is unchanged.
- New CI job `build_test_js_lnx`: build the addon, run `node --test test/js/`.
- The real acceptance test is PRD-015's case list (its milestone M5).

## What was built (differences from this plan)

Three decisions were taken during implementation that this document did not
anticipate. They are recorded here rather than edited into the text above, so
the plan and what happened stay distinguishable.

**1. The whole Python surface, not a first slice.** *Non-goals* proposed
deferring `sim`, `hmm`, `nn`, `pda`, `superres` and `localization`. Instead
`ext/js/tttrlib.i` has an `%include` list **identical** to
`ext/python/tttrlib.i`'s. The subset was not cheaper: the shared fragments are
one dependency graph and the guards a subset needs are most of the guards the
whole needs, and the burst and single-molecule applications this binding exists
for reach into the simulator and the decoders the way the Python tools do.

**2. `shared_ptr` had to be *designed*, not merely transcribed.** SWIG 4.2 ships
`boost_shared_ptr.i` for python/, r/ and java/ but **not** for javascript/napi/,
so `%shared_ptr(TTTR)` expanded to an undefined `SWIG_SHARED_PTR_TYPEMAPS` and
nothing built. The obvious move — transcribe SWIG's own version — was tried
first. It compiles cleanly and is useless: **every method call fails at run
time**, with `in method 'TTTR_get_macro_times', argument 1 of type 'TTTR *'`.

Every other language's shared_ptr support rests on the proxy object holding a
`shared_ptr<T>*` registered under the shared_ptr's own type. The Node-API
backend's generated ObjectWrap constructor cannot: it hard-codes

    this->info = SWIGTYPE_p_TTTR;    // always the RAW class type
    this->self = result;             // always the raw `new TTTR(...)`

so a JavaScript-constructed object holds a raw pointer under the raw type, and
every typemap asking for the shared_ptr descriptor misses.

`ext/js/js_shared_ptr.i` therefore inverts the assumption: the proxy always holds
the **raw `T*`**, and the C++ reference lives in a refcounted holder table keyed
by that pointer. The table also disambiguates destruction — a pointer in it came
from a `shared_ptr` and is released; one that is not came from `new` in a
JavaScript constructor and is deleted.

Its one limitation is stated in the file and in the package README: an object
constructed in JavaScript and handed to C++ that stores a `shared_ptr` is passed
with a null deleter, so C++ holding it does not extend its life. That is the
contract R and Java already live under, and lifting it would need the proxy to
hold a `napi_ref`, which a typemap cannot reach.

**3. `std::vector<T>` needed typemaps too.** SWIG's Node-API `std_vector.i`
wraps vectors as opaque proxies with `.size()`/`.get()`, as the Java backend
does; Python's converts to and from a list. Without conversion every
vector-returning method — the six burst searches, the correlator curves, the
decay histograms — would have come back as something a caller has to loop over
element by element. `jsarrays.i` adds `std::vector<T>` ↔ TypedArray for every
numeric element type.

Three SWIG behaviours cost real time and are worth knowing before touching these
files again:

- A multi-pattern `%typemap(A, B) (locals)` attaches the locals to the **last**
  pattern only. Declaring `ARGOUTVIEW` and `ARGOUTVIEWM` together left every
  `ARGOUTVIEW` wrapper referring to an undeclared `data_temp`.
- Typemap locals are **not** emitted for the constructors of a
  `%template()`-instantiated class. The `std::vector` reference typemaps
  therefore allocate and let `freearg` release, using no locals at all.
- The SWIG preprocessor reads a backtick, and the macro-end directive spelled
  out, **inside comments** in a macro body. Either silently truncates the macro,
  and the error points hundreds of lines away at the macro's opening.

**4. Packaging was a relocatability problem, not a metadata problem — and
`prebuildify` could not be used.** *Packaging* above assumed the shape of the
work was "run `prebuildify`, upload". Neither half held.

`prebuildify` shells out to `node-gyp`, which needs a `binding.gyp` describing
the whole build. This addon is a CMake target linking 35 module libraries,
HDF5, OpenMP and a vendored libtiff; a second, hand-maintained description of
that in `binding.gyp` is precisely the drift this project avoids everywhere
else. Only the *output* is a contract — `prebuilds/<platform>-<arch>/` with
`node.napi[.<libc>].node` inside — so `scripts/prebuild.mjs` produces that
layout from CMake and `node-gyp-build` resolves it unchanged. The published
tarball ships binaries only; there is deliberately no source fallback, because
a fallback that cannot work is worse than an error message that names the
missing triple.

The real work was that **the built addon was never relocatable**. It linked
~35 sibling `libtttrlib_*` libraries plus HDF5 and libomp through absolute
build-tree RPATHs, and `ext/CMakeLists.txt` carried a comment asserting the
module libraries "sit next to the addon in js-pkg/, the same layout the npm
package ships" — describing a staging step that did not exist. Everything
worked because every test ran on the machine that built it. Three changes
follow:

- prebuilds are built `-DTTTRLIB_MODULE_TYPE=STATIC`: one 14 MB `.node` with
  two external dependencies instead of 35 sibling libraries with dozens. The
  risk this raises is real and specific — a static archive can drop the
  translation units whose only purpose is a registration side effect — so the
  smoke test counts registry entries rather than merely loading the binary
  (52 entries across 11 areas, 7 burst searches, 14 containers);
- the artefact comes from `cmake --install --component js`, never a copy out of
  the build tree. Only *install* rewrites RPATHs to `@loader_path` / `$ORIGIN`;
  a copied binary is indistinguishable from a correct one until it reaches a
  machine without the build directory. `install(RUNTIME_DEPENDENCY_SET)`
  collects the third-party libraries and fixes their install names too;
- `prebuild.mjs` **verifies** rather than trusts: every dynamic dependency must
  resolve inside the prebuild directory or to an OS library, no RPATH may be
  absolute, and it refuses to emit a prebuild that fails either check. This is
  the check the missing staging step needed and never had.

**5. A concurrent change had already broken the registry-driven surface.**
PRD-032 replaced the burst-search JSON literal with registrations, and its
verification reported "0 entries changed" — a comparison of *parsed* JSON,
which is exactly the step that discards key order.
`TTTR::burst_search_algorithms_json` round-tripped through `nlohmann::json`
(a `std::map`), sorting `params_schema.properties` alphabetically. That order
is the C++ argument order, and JavaScript has no `**kwargs`, so
`burstSearchByName` began passing `max_false_alarm_rate` where `p0` belongs.
Python never noticed. Fixed to `nlohmann::ordered_json`, and the invariant is
now pinned: `required` preserves declaration order, so it must be a subsequence
of the property keys — which sorting breaks immediately.

The general lesson is worth more than the fix: **the JavaScript binding is the
project's only consumer that depends on registry key order**, so a registry
change that Python, R and Java all survive can still break it silently.

## Risks

- **Everything blocks the event loop.** A synchronous 200 MB PTU read stalls the
  Node process — fine for a CLI, fatal for a server. v1 mitigation: PRD-017 runs
  the analysis in a `worker_thread`. If that proves insufficient, the async
  wrappers are the one concrete reason to revisit the fork decision.
- **External ArrayBuffers.** `napi_create_external_arraybuffer` is the basis of
  zero-copy `ARGOUTVIEW` and is *not* supported in every Node-API runtime
  (Electron notably restricts it). Mitigation: a compile-time
  `TTTRLIB_JS_COPY_ARRAYS` fallback that copies, and a runtime probe that says
  which mode is active. Decide this in M2, not after the API is public.
- **Lifetime bugs are segfaults, not exceptions.** A `TypedArray` outliving the
  `TTTR` that owns its memory crashes the process. Every `ARGOUTVIEW` must keep a
  reference to the owner in its finalizer, and the test suite needs an explicit
  "drop the owner, then read the view" case run under ASAN.
- **A fourth backend in the `int64_t` matrix.** The `-DSWIGWORDSIZE64` constraint
  is documented as a three-way interaction between SWIG version, backend and
  platform. Verify JS generation with SWIG 4.2 *and* 4.4, with and without the
  flag, before merging — the same sweep that was needed for R.
- **Unwrappable surface discovered late.** Directors are known-out; what else is
  will only appear when the full `.i` set is fed to the backend. M1 exists to
  find that early and cheaply.
