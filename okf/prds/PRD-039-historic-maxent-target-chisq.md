# PRD-039 — Historic MaxEnt: joint chi²+nu optimization (auto-nu via a target chi-square)

**Status:** 🟢 Done (2026-08-13; search redesigned 2026-08-14 after the
original bisection failed on a steep case — see "The rework").
**Depends on:** PRD-038 (the shared `MaxEntQp.h` engine both MaxEnt callers
now route through).
**Method note:** implemented test-first per instruction ("before impl in cpp
test in python") — a pure-Python prototype on the existing
`tcspc_run_mem` binding was validated (including against simulator-generated
photons, per "the maxent solver must be tested against sim data generated by
sim") before any C++ was written; the prototype stays in the test file as the
reference implementation the C++ is asserted to agree with.

## The questions that opened this

1. *"Is the MaxEnt general enough to support arbitrary axes / lifetime
   spacings?"* — **Yes, already; nothing was changed for it.**
   `tcspc_build_fi_lifetimes` / `tcspc_build_fi_distances` take a
   caller-supplied `tau` / `R` array and loop over each entry independently —
   no spacing, ordering, or log/linear assumption anywhere. `decay_pattern_fit`'s
   `patterns` is a fully arbitrary `vector<vector<double>>`. Log-spaced,
   non-uniform, irregular grids all work as-is.
2. *"Isn't there a regularization-free algorithm — optimize regularization
   and chi² simultaneously?"* — Not in tttrlib, and not in chisurf either.
   The user chose to add one: the classic **"historic MaxEnt"** criterion —
   find nu such that the fit's chi-square lands at a caller-chosen target —
   as an explicit opt-in mode.

## The honesty framing (read before using this)

chisurf — whose `maxent_decay.core.solver` this engine was ported from —
**deliberately does not implement** target-chi² nu selection. Its
`docs/concepts/maximum_entropy.md` argues the technique is statistically
naive for decay data: *"ν is not a nuisance parameter to fit... this is why ν
cannot be chosen by goodness of fit: the wrong answer fits better."* What
chisurf offers instead is an opt-in L-curve sweep (`run_lcurve_handler`,
`geomspace(center*1e-2, center*1e2, 16)`) whose corner is a *suggestion*
surfaced to the user, never auto-applied.

This PRD adds the target-chi² search anyway, because it was explicitly
requested as a capability beyond the reference — but as an **opt-in mode
that is never the default**, with the caller told to watch the `converged`
flag. The L-curve workflow remains the better-justified way for a human to
pick nu.

## What was built

**Engine** — `modules/math/include/MaxEntQp.h` / `src/MaxEntQp.cpp`:
`MemTargetChisqResult` (composes `MaxEntResult`; carries `nu`,
`outer_niter`, `converged`) and

```cpp
MemTargetChisqResult run_mem_target_chisq(
    H, g0, m, const_chi2, target_chisq,
    nu0 = 1e-5, max_iter = 1000, chisq_tol = 1e-2,
    tol = 1e-4, min_prob = 1e-12);
```

A **joint (p, nu) controller, Gull-Skilling style**: each iterate takes one
bound-QP Newton step on the amplitudes at the current nu, then moves
log(nu) toward the value whose chi-square matches the target — a secant
step in (log nu, log chisq) space over the last two iterates, falling back
to a damped multiplicative move when the secant is unusable, clamped to a
factor of 30 per iterate so the warm start stays useful. The amplitudes
carry across nu changes, so the whole search costs about one `run_mem`,
not twenty. `run_mem`'s Kahan quadratic was extracted to a shared
`mem_chisq` helper (pure move) so the ceiling can reuse it; the
Skilling-Bryan TEST quantity likewise became shared `mem_dgrad`. Not
SWIG-bound directly (internal engine, like the rest of `MaxEntQp.h`);
reached through the two caller surfaces below.

## The rework: why it is not an outer bisection

The first implementation was an outer root-find — bisection in log(nu) with
geometric bracket expansion, cold-starting the fixed-nu `run_mem` once per
nu probe. It passed every analytic and sim-data test at 2×10⁵ photons, and
**failed on the first steep real case it met**: the 1×10⁶-photon FRET
figure (Gaussian distance distribution, 100-point R grid) that prompted this
rework. There the chisq(nu) transition is steep, and the bisection exhausted
500 cold-started MEM solves (~143–195 s over two replicated runs) stuck at
chisq 0.98 against a target of 1.0 — `converged=false`. The failure is
structural, not a tuning miss: each probe pays a full MEM convergence just
to sample chisq(nu) once, and one sample per ~40× nu step is too little
information near a steep transition. The joint controller — designed and
measured in a Python prototype against that exact failure first — lands at
chisq 1.0000 in 157 warm-started QP steps (~4 s, all in C++); the prototype
A/B measured 300 QP solves / 1.4 s against the bisection's failure at
194 s. The regression test
`TestTcspcMemFret::test_target_chisq_converges_on_a_steep_fret_case` pins
that exact fixture so a return to an outer root-find fails loudly.

**Two prototype-phase findings that shaped the algorithm** (both would have
been C++ debugging sessions without the Python-first step):

- **No nu=0 floor precheck.** `run_mem` at exactly nu=0 lands *above* the
  truly reachable chi-square floor (measured on a 60-column lifetime grid:
  1.679 at nu=0 vs 0.919 at nu=1e-8), because the unregularised QP on the
  near-singular H is ill-conditioned while a tiny nu>0 acts as an
  interior-point regulariser. The floor is discovered by the controller
  driving nu down to its clamp (1e-30); pinned nu plus stationary
  amplitudes means every later iterate repeats, so the loop stops and
  reports `converged=false` for an unreachable-low target.
- **The nu→∞ ceiling is analytic.** p→m, so the ceiling is the quadratic
  form at the prior — zero solves. A target at/above it returns the prior
  itself with `nu=+inf`.

Monotonicity of chisq(nu) is provable only for the exact minimiser
(`quadpr_bound` is not KKT-correct; the loop stops at finite tol), so the
controller tracks the best-observed iterate across everything it evaluated
and returns that — and both test files carry an explicit empirical
monotonicity sweep so a real violation fails CI rather than fielding.

**Iteration counts worth knowing before tuning defaults:** a fixed-nu
`run_mem` converges in ~20 outer iterations on the test fixtures, but
interleaving the nu moves stretches the same convergence to several hundred
(measured: 647 on the 60-column lifetime fixture from seed nu=1e-5, 157 on
the 100-column FRET fixture). That is why `run_mem_target_chisq`'s default
cap is 1000 and both callers floor their `max_iter` at 1000 in target mode
— a fixed-nu-appropriate cap of 200 would silently under-run the search.

**Caller 1** — `decay_pattern_fit` gains `PatternFitMode::kMaxEntTargetChisq`:
`reg_strength` is reinterpreted as the target chi-square (**raw-sum units**,
natural value ≈ `data.size()`), `PatternFitResult` gains `nu_used` /
`target_converged`. Documented footgun: flipping a `kMaxEnt` call to
`kMaxEntTargetChisq` without updating `reg_strength` reads a tiny nu as an
unreachably-low target — graceful `target_converged=false`, never a crash.

**Caller 2** — `solve_tcspc_mem_lifetime` / `solve_tcspc_mem_fret` gain a
trailing defaulted param: `target_chisq = -1.0` (≤0 = disabled, the
untouched fixed-nu path; >0 = auto-nu, and `nu` then **seeds** the
controller). `MemTcspcResult` gains `nu_used` /
`target_chisq_converged`. **Units differ from caller 1 and it matters**:
this solver's H/g0/const are divided by the fit-bin count, so its chi-square
is a MEAN — the classic historic-MaxEnt target here is **~1.0, not the bin
count**. SWIG: the two hand-written `%inline` wrappers in
`ext/python/MaxEntTcspc.i` carry the same keyword param (Python/R/JS;
Java was already excluded from this file); `DecayPatternFit.i` needed no
edit (generic `%include`, all four languages).

Out of scope, deliberately: `maxent_invert` (corrections module) — its
`nu_run = 2·nu²` reparametrisation makes a target-mode signature awkward and
nobody asked for that path. Same trailing-param pattern applies if wanted.

## Verified

- **Python prototype first** (`_mem_target_chisq_reference`, kept permanently
  in `test_maxent_tcspc.py` as the statement of what the C++ computes):
  validated on the analytic Poisson fixture and on simulator-generated
  photons before the C++ existed.
- **Sim-data gate** (`TestTcspcMemOnSimulatedPhotons`): decays generated by
  `SimEngine` (config-driven, known lifetimes, Gaussian IRF handed to both
  simulator and fitter, `background` zeroed because the simulator's
  unconfigured background is a micro-time-0 spike). Single lifetime 2.5 ns:
  fixed-nu and auto-nu (`target_chisq=1.0`) both recover it (mean tau within
  0.25 ns, >70% mass within ±0.5 ns); two lifetimes 1.0+4.0 ns come out as
  two mass groups. Sim parameters matter: a 0.3 ns IRF at 1024 bins keeps
  the simulator's pattern sampling and the fitter's trapezoidal `fconv`
  consistent below Poisson noise at 2×10⁵ photons (floor mean-chi² 0.92); a
  0.1 ns IRF at 512 bins leaves visible model mismatch (floor 1.38) — that
  discretisation residual *scales with photon count*, which is why the
  two-lifetime test probes the floor and targets `floor×1.2` instead of
  betting on 1.0 being reachable.
- **C++ agrees with the frozen prototype exactly**: found nu to 1e-6
  relative, chi-square to 1e-6, amplitudes to 1e-9, on both the analytic
  fixture and sim data (`TestSolveLifetimeTargetChisq`, and inside the sim
  test).
- **The steep-FRET regression case** (the bisection killer): 1×10⁶ photons,
  100-point R grid, target 1.0 — converges to chisq 1.0000 in 157 QP steps
  (~4 s in C++); recovery mean 44.2 Å / sd 5.1 Å against truth 45/4, with
  bands wide enough to catch both classic MEM failure modes (spiky collapse,
  over-regularised smear). The same fixture drives the gallery example
  `examples/fluorescence_decay/plot_maxent_fret_recovery.py` (fixed seeds),
  which generates `doc/img/maxent_fret_distance_recovery.png` — the figure
  showing all three regularisation regimes side by side.
- **Monotonicity of chisq(nu)** asserted empirically through both public
  surfaces (`tcspc_run_mem` sweep; `decay_pattern_fit` kMaxEnt sweep).
- **Both impossible-target directions degrade gracefully** (low → floor fit,
  `nu_used` tiny/0; high → prior fit, `nu_used=inf`; `converged=false`, no
  crash) in both callers.
- **Backward compatibility**: `target_chisq=-1.0` produces byte-identical
  results to the pre-change call (asserted); all pre-existing cases pass
  unchanged (50 across the three touched files after the rework:
  `test_maxent_tcspc.py` incl. the new regression test,
  `test_decay_pattern_fit.py`, `corrections/test_corrections.py`).
- Full `test/python/` suite run after the change (see CHANGELOG entry).
