# tttrlib for Node.js

Read, correlate and analyse time-tagged time-resolved (TTTR) single-molecule and
FLIM data. This is the tttrlib C++ core, wrapped for Node.js — the same core the
Python, R and Java bindings use, generated by SWIG from the same interface files,
so the numbers cannot differ between them.

```js
const tttrlib = require('tttrlib');

const t = new tttrlib.TTTR('measurement.ptu');
console.log(t.size(), 'photons');
console.log(t.macroTimes);          // BigInt64Array
console.log(t.microTimes);          // Uint16Array
console.log(t.acquisitionTime, 's');

const [decay, time] = t.getMicrotimeHistogram(1);
```

## Four things to know

**64-bit values are BigInt.** Macro times exceed 2<sup>53</sup>, where a
JavaScript `number` stops being exact. They cross as `BigInt64Array` and scalars
as `bigint`. Summing them needs `0n` as the seed:

```js
const total = t.macroTimes.reduce((a, b) => a + b, 0n);
```

Reductions you would otherwise be tempted to do in `Float64Array` are available
in C++, where they are both exact and faster.

**Multi-dimensional results are flat, row-major, with a `shape` property.**

```js
const img = new tttrlib.CLSMImage(t).getIntensity();
img.shape          // [frames, lines, pixels]
img[(f * lines + l) * pixels + p]
```

The same form is accepted as input, as are nested arrays and `{data, shape}`.

**Containers are native values.** `std::vector` comes back as a TypedArray and
`std::map` as a plain object — not the opaque proxy SWIG's Node-API backend
produces by default, and matching the list/dict Python's binding gives:

```js
correlator.getCorrNormalized()        // Float64Array
extractor.getBurstChannelPhotons()    // { "0": Float64Array, "8": Float64Array }
```

**Every method has two names.** The C++ name (`get_macro_times`) and a camelCase
alias (`getMacroTimes`); a `get_x`/`set_x` pair also appears as a property `x`.
Use whichever reads better — code ported from the Python binding keeps working,
and so does code written against the C++ documentation.

## The registry: don't hard-code algorithm lists

`registry()` returns a machine-readable description of what this build can do —
which burst searches exist, which containers it reads, and a JSON Schema of every
parameter with its default, unit and range. A user interface built from it gains
new tttrlib features on upgrade with no code change:

```js
for (const name of tttrlib.burstSearchAlgorithms()) {
  const bursts = t.burstSearchByName(name);   // defaults from the schema
}
const schema = tttrlib.registry('burst_search').sliding_window.params_schema;
```

## Zero copy, and when it isn't

Array results are normally views over C++-owned memory rather than copies. Two
consequences:

- A view returned by a `getX()` accessor is valid only while the object it came
  from is alive. Reading it after the owner is collected is a use-after-free, not
  an exception. Call `.slice()` if it must outlive its owner.
- Some Node-API hosts refuse external `ArrayBuffer`s (Electron, and builds with
  the V8 sandbox). The binding detects that at run time and copies instead;
  `tttrlib.arraysAreZeroCopy()` reports which mode is live, and building with
  `-DTTTRLIB_JS_COPY_ARRAYS` forces copying everywhere.

## Blocking

Every call is synchronous. Reading a 200 MB file takes seconds and blocks the
event loop for all of it, so in a server put the work in a `worker_thread` —
`examples/js/ptu-webapp/` in the repository shows the shape of that.

## Building from source

```
cmake -S . -B build -DBUILD_JAVASCRIPT_INTERFACE=ON
cmake --build build -j
```

Needs SWIG ≥ 4.2 (the Node-API backend landed there) and `npm install` in this
directory for the `node-addon-api` / `node-api-headers` headers. The result is
`build/js-pkg/tttrlib.node`, which this package's loader finds without
installation.

Node ≥ 12.17. Node-API's ABI stability means one binary serves every later Node
version without a rebuild.

## What is not here

- **Directors.** SWIG's Node-API backend generates none, so `PdaCallback` cannot
  be subclassed from JavaScript — the same limitation the R binding has. PDA's
  built-in models are unaffected.
- **Promises.** Everything is synchronous; see *Blocking* above.
- **The browser.** This is a native addon for Node. A WASM build is a separate
  question, and not a small one.
